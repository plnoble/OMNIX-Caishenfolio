## 2. 已直接处理：FA1-R01（P1）普通单测启动真实桌面

### 事实与影响

原 `tests/Caishenfolio.Desktop.Tests/WpfTestHost.cs` 创建生产 `App`、执行 `InitializeComponent()`，随后 `Dispatcher.Run()`，并声称不调用 `App.Run()` 就不会触发 StartupUri。

这个假设不成立：WPF `Application` 构造时已将启动工作排入 Dispatcher；生产 App 的资源初始化又设置了 `StartupUri=MainWindow.xaml`。Dispatcher 开始运行仍会创建真实 MainWindow，进而打开正式状态路径、自动启动核心。可对照 [WPF Application 源码](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Application.cs) 的构造函数与 DoStartup。

本轮第一次独立运行关闭了真进程门控，615 项表面通过，却留下：

- 19:17:21 创建的 python launcher 18584，父进程 34632；解释器 19180 是其子进程。
- `/health` 为 `cache+upstream`、`synthetic=false`，正式 `bars_cache.db` 路径；不是隔离 fixture 核心。
- 这足以否定“普通控件单测不启动真实桌面”的保证，也使旧“真进程五项均自启”的推断不充分；不能仅凭测试计数排除复用残留核心。

### 修复与验证

只改测试侧三个文件：

1. `WpfTestHost.cs`：使用普通 `Application`，不实例化生产 `App`；只提取真实 App.xaml 的 `Application.Resources`，保留 STA/Dispatcher 与串行编组。初始化错误传递给测试，不无限等 Ready。
2. `Caishenfolio.Desktop.Tests.csproj`：编译时嵌入当前生产 App.xaml，资源不手抄、不另维护一套主题。
3. `WpfTestHostIsolationTests.cs`：等待 Dispatcher 到 ApplicationIdle 后，断言 Application 类型、StartupUri 为空、MainWindow 为空、窗口集合为空，且真实主题资源可用。

完整 C# 616 项通过；门控关闭时测试后无核心进程、无相关端口监听。随后在空闲端口和 fixture 环境下独立执行五项真进程测试，5/5 通过，结束后无残留。

修复过程两次失败亦保留：派生 App 与已编译 BAML 类型不兼容；StartupUri setter 拒绝 null。最终实现不采用这两条路径。对应日志为 `csharp-fixed.log`、`csharp-fixed-2.log`；它们不是通过结果，最终以 `build-verified.log` / `csharp-verified.log` 为准。

本轮只停止了逐项核对 PID、创建时间、父子关系后的上述自有残留核心，没有停止用户其他应用。正式账本主文件本轮观测指纹与交付包一致，未见 WAL/SHM；**不据此声称正式状态目录未被访问或整个目录未发生变化**。

## 3. 尚未闭环的验收问题

### FA1-R02（P2）：首次引导的等待与窗口归属不足

位置：`scripts/ui_smoke.ps1` 的 `Invoke-DismissOnboarding`（约 147–191 行），调用点约 1136 行。

- 每次冒烟新建隔离账本，但引导仅被查找一次；查不到就记“非首次启动，未出现”并通过。
- 实际 MainWindow.Loaded 先显示模态引导、关闭后才启动核心。因此主窗口标题先出现、引导稍后出现时，脚本可漏掉引导，随后误报核心 60 秒超时。
- 查找引导只按标题，在全桌面范围搜索，没有使用传入的 ProcessId。另一实例的同名引导可能被误操作。
- 原 `ui-run-1.log` 的失败尝试确有“非首次启动，未出现”随后核心超时。上述是可从代码确认的缺口和合理诊断线索，**尚不能认定它解释了全部历史超时**。

完成标准：只操作本次 PID 的窗口；新隔离根应有引导，延迟出现须有界等待，超时明确失败，不能当非首次通过；关闭后确认本次引导确已消失。补“延迟出现”“另一 PID 同名窗口”回归，并运行真实隔离启动验证。

### FA1-R03（P2）：失败证据覆盖，启动稳定性尚不能确认

位置：`scripts/ui_smoke.ps1` 约 975–978、1082–1084、1297 行及原交付 §4/§8。

- 两份成功 JSON 都指向同一个 `desktop-stdout.log` / `desktop-stderr.log`；每次启动会删除旧日志，`core-runtime.log` 也被覆盖。
- `ui-run-1-report.json` 是 15:33 成功，`ui-run-1.log` 却是 15:31 失败；现存 core-runtime 仅记录 16:07 的最后一次成功启动。不能宣称每次失败现场完整留存。
- 时间线缺少第 11 次成功运行的完整开始/退出记录，第 9 次也缺结束结果。§4 列 #5–#8 与 #10 共五次核心超时，却写“约 4/11”；#11 与 run-2 的总尝试数也未统一。不能据此计算可靠失败率。
- “有时两秒启动、桌面无异常”不足以证明与源码无关：核心标准输出/错误被 Broker 重定向但未纳入这些桌面日志，桌面启动异常也可能只显示在 UI。

完成标准：每次启动创建独立 attempt 子目录，报告、输出、错误、核心诊断、开始/结束/退出码与源码指纹一一对应，拒绝覆盖已有证据；保留全部失败。修好可确认的等待/归属缺陷后，先约定连续冷启动样本再执行，不因失败而重置计数挑绿灯；最后串行跑两次完整 UI 冒烟。未定位失败原因则保留 unresolved，而不是自动归为环境问题。

建议固定做 5 次隔离冷启动用于排查，遇到失败先保存现场并定位；这是诊断样本，不是统计可靠性承诺。旧孤儿核心问题与冷启动超时分别追踪，不强行归为同一根因。

以上两项组成一个“启动与验收工具可靠性”收尾单元；不再拆成反复小交接。不要重写业务、扩大金融功能或要求重做已关闭的 R7。
