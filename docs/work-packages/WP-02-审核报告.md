   JPY 现金在估值时被跳过，但明细账户仍固定 `ValueKnown=true`，于是市值为 0、净投入为 100、累计收益为 **−100 CNY**。新汇总只检查账户收益是否为 null，收不到未知状态，首页也显示确定亏损。**汇总层的 null 传播正确，但源头已经把未知变成了零。**

2. **FIFO 只接到了批次表，结果卡和后台提醒仍使用移动均价。**  
   位置：[LedgerHeldCostPrefill.cs:29](D:/Agent/Worktrees/OMNIX-Caishenfolio/wp-02-verify/src/Caishenfolio.Desktop/Wealth/LedgerHeldCostPrefill.cs:29)、[BackgroundExtendedCheck.cs:264](D:/Agent/Worktrees/OMNIX-Caishenfolio/wp-02-verify/src/Caishenfolio.Host/Notifications/BackgroundExtendedCheck.cs:264)。  
   复现：先用 `100 CNY` 买 `2,000 JPY`，再用 `200 CNY` 买 `2,000 JPY`，然后换出 `2,000 JPY`。当前 USD/CNY=7.5、USD/JPY=150。  
   FIFO 剩余成本应为 **200 CNY**，但预填和提醒取得的均价成本为 **150 CNY**。剩余 JPY 的市值为 100 CNY，因此：
   - FIFO：盈亏 **−100 CNY**，临界 USD/JPY **75**。
   - 当前结果卡：盈亏 **−50 CNY**，临界 USD/JPY **100**。  
   
   Python 公式本身正确，输入成本却没有采用本包声明的 FIFO 口径。

**建议与覆盖风险**

- 优先用上述输入补端到端断言。目前 A4 只覆盖两段换汇，无法发现深层比例与支路汇合错误；三态测试手工构造 `BackgroundCheckResult`，未覆盖整轮抛异常；累计收益未知测试只覆盖余额账户未报数，漏了明细账户未定价。
- 净 diff 中未发现既有业务断言被删除或放宽，也未发现断言前篡改被测结果的做法。**仅凭净 diff，不能判断中间提交是否曾为变绿修改预期。** DTO 手工夹具属于正常测试安排，但不能证明真实流水到结果卡的成本口径一致。
- 新增夹具未见本机用户名或包含账户名的绝对路径；金额有合成声明。未接触真实账本，无法独立认证金额来源。
- 同日批次在消费时按 `AcquiredOn→Id` 排序，重放却按 `TradeDate→RecordedAt→Id` 排序。这是顺序契约风险，建议补同日反向 ID 用例并明确裁定；本次不将其列为确信错账。

R1 本身审查通过：`T=(持有量/历史成本)×USD/CNY` 的单位正确；`required_move_pct=(r−T)/r` 的符号正确；旧 `breakeven_held_rate=th/tb` 保留。普通换汇冲正会重建投影、撤销相应批次及消耗，本段成本也确实记录付款币种与手续费。历史成本为 None 的 Python 路径保留到账额，没有直接把未知收益、归一化值或变动百分比填成 0。

**我认为最可能被漏掉的一个错账场景：旧 JPY 全部取出，后来存入同金额、无购入回单的 JPY，再换成 USD。** 现金余额看起来正常，批次却复用了已经离开的旧成本，甚至不会产生“未被批次覆盖”警告。
