1. **[P1] 旧规则在加载后仍没有 Id，后台保留原碰撞，编辑第二条还会覆盖第一条。**

   **文件:行：** `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml.cs:382`、`:414`、`:284–296`；`src/Caishenfolio.Host/Notifications/NotificationSettingsStore.cs:24–25`、`:39–40`；后台入口 `src/Caishenfolio.Desktop/App.xaml.cs:44–56`。

   **触发输入：** 旧设置有两条 `Id=""` 的 CNY/JPY/USD 净到账规则，阈值均为 1000，固定费分别为 0、2。升级后直接后台检查，或打开设置页，选中第二条，载入并把阈值改成 1200，再点“应用修改”。

   **会出什么错：** `Load()` 原样反序列化，后台从未调用 Save/Reconcile，所以两条旧规则仍共享 fallback 身份，上一轮“第一条已发、第二条首次满足却被冷却压掉”的输入继续成立。编辑时 `_editingRuleId=""`，`FirstOrDefault(r => r.Rule.Id == editing)` 命中第一条：第一条被改成阈值 1200、固定费 2，真正选中的第二条仍是 1000。

   **为什么是缺陷：** 空 Id 是本次升级的正常输入，不是损坏数据。仅在保存时补身份，无法保证此前的生产评估和编辑正确；修改选中规则还会静默破坏另一条规则。应在规则进入消费路径前完成持久身份迁移，并避免用尚未唯一化的空 Id 定位行。

2. **[P1] 补随机 Id 没有迁移已有的带 `|rule:` 状态键，会在冷却期内重发。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleIdentity.cs:31`、`:90`；`src/Caishenfolio.Host/Notifications/NotificationSettingsStore.cs:39–44`；迁移接点 `src/Caishenfolio.Host/Notifications/AlertGatekeeper.cs:146–156`、`:181–185`。

   **触发输入：** 空 Id 的旧规则在 09:00 已送达，状态只有 `FxNetArrival|JPY/USD|净到账达到你设定的目标|rule:NetArrivalAbove:?:CNY/USD/JPY@r0#amt:1000`，没有裸前缀键；冷却 12 小时。09:10 不改规则、仅保存设置，09:20 再检查且条件一直满足。这个状态既可由基准版本产生，也可由本版先 Load 旧设置、后首次触发产生，不要求曾发布中间版本。

   **会出什么错：** Save 为规则补成 `rule-…`，完整通知键随之改变。`AdoptLegacy` 只查精确的裸键 `Kind|Symbol|Title`，不会查同前缀下另一个含 `|rule:` 的键；于是 `previous=null`，09:20 再发。若先发生 UNKNOWN，旧完整键也不在新 UNKNOWN 集合或裸前缀集合中，会被当作退出。

   **为什么是缺陷：** 用户没有改变观察条件，单纯补身份却丢失送达历史，违反 A9/D6。现有“前缀收养”并不等于“收养所有共享前缀的完整键”。需要明确的旧身份到新身份迁移，且不能把所有同前缀新规则永久合并冷却。

3. **[P2] `G29` 消除了精度碰撞，却改变已有 Level 的字符串；“不会科学计数”的说明与测试假设错误。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleEvaluator.cs:100–114`；`tests/Caishenfolio.Host.Tests/AlertIdentityTests.cs:193–227`。

   **触发输入：** 使用已经有持久 Id、Revision 不变的 RateBand 规则，下限为 `0.00001m`，已有状态键含 `#band:0.00001~-`，仍在冷却期。升级后保持同一输入。

   **会出什么错：** 新 Level 为 `band:1E-05~-`，完整键不匹配且没有旧 Level 别名迁移；条件仍满足也会被当作首次发送。`-0.00001m` 同样从 `-0.00001` 变为 `-1E-05`。`7.1000001/7.1000002` 确实分别保留了完整值，但两者原来的 `7.1` 键也不能直接遗忘。

   **为什么是缺陷：** 精度修复必须配套历史键兼容。按照 [.NET 官方 G 格式规则](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-numeric-format-strings#general-format-specifier-g)，指定精度后，科学计数指数小于 -4 时会使用科学计数法；decimal “始终定点”的例外只适用于未指定精度，不能套到 G29。大数测试选择了 `10^26`，并不能判别小数侧的漂移。

   **边界核对：** G29 足以保留 decimal 的有效数字；decimal 最大/最小值的指数是 28，仍用定点表示；最小正量 `10^-28` 会是 `1E-28`，旧六位格式则是 `0`。普通尾零值 `1000.00`、`3.0`、`7.10`、`0.00` 的结果仍分别是 `1000`、`3`、`7.1`、`0`。未发现新的数值精度碰撞；问题是键兼容，不能仅以“大数没有 E”证明无漂移。

4. **[P2] 重复保存同一份输入不稳定：空 Id 会重分配，旧 Revision 还会回退。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleIdentity.cs:90–101`；`src/Caishenfolio.Host/Notifications/NotificationSettingsStore.cs:37–45`；生产调用 `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml.cs:660–666`、`:689`；测试 `tests/Caishenfolio.Host.Tests/FxRuleIdentityPersistenceTests.cs:110–120`。

   **触发输入：** ①设置页加载空 Id 旧规则，连续点“发送测试通知”，或点一次后再保存。②存储已有规则 A/r0/阈值1000，调用方构造同 Id、仍为 r0、阈值1200 的 `changed`，连续执行两次 `Save(changed)`，不替换原输入。

   **会出什么错：** ①Save 返回的补 Id 副本没有回填 `_fxRules`；每次 `ReadNotificationForm` 又提交空 Id，Reconcile 每次生成新 Id。②第一次保存正确写成 r1；第二次参数已经相同，`WatchChanged=false`，直接把输入的 r0 写回，Revision 从 1 降到 0。已有通知状态因此再次换键，可能重发或误用旧冷却。

   **为什么是缺陷：** Save 现在是不可变副本转换，真实调用方却仍持有旧对象；Reconcile 只在参数不同的分支处理版本，没有保证相同观察条件保留已存版本。新增“幂等”测试只执行 `Reconcile(first, first)`，始终把已修正输出同时当作输入和存储，覆盖不到实际重复保存路径。问题不是每次都 +1，而是身份重建和版本回退。

8. **[P3] 修改成功后总是提示“内容没变”。**

   **文件:行：** `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml.cs:384–390`。

已确认成立的部分及边界：

- **新建与落库：** 设置页 `BuildFxRule → AssignNewIdentity` 和添加按钮已走真实路径；所有找到的生产 `NotificationSettingsStore.Save` 调用都会经过 Reconcile。未发现本轮新增绕过它、直接向 `notifications.json` 落库的生产调用。直接构造 NotificationSettings 再调用 Save 也会补 Id；直接 `ToJson/FromJson` 的旧测试辅助仍不补 Id，它们不是生产落库路径。后台/App 的问题是 Load 后消费旧空 Id，见第 1 条。
- **正常编辑的 Revision：** 对已有唯一 Id 的规则，一次参数修改由 `WithEditedParameters` 推进一次；随后 Save 看到版本已经更大，不会再 +1。未修改或仅用启用列切换时，WatchChanged 不推进版本；参数字符串的首尾空白、大小写经 Normalize 比较。规则没有可编辑备注字段，通知 Message 不入键。已推进的版本通常拥有独立冷却；若仍有裸旧前缀记录，保守收养可能暂时压制一次，这是 D6 已接受的迁移取舍。
- **删除重建：** 当前设置页删除后重新添加会生成新 Id，不会按相同参数找回旧 Id。修改保留 Id 的正常路径成立，但旧空 Id 行的选择和升级迁移仍需修复。
