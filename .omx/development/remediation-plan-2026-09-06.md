## 4. 工作包一：保证组合交易后权重守恒

### 4.1 当前问题

涉及文件：

- `python/caishenfolio_core/research/evidence_card.py`
- `src/Caishenfolio.Desktop/Wealth/EvidenceCardView.xaml.cs`
- `tests/python/test_evidence_card.py`

当前实现把候选资产权重直接加到原地区/币种权重上，没有同步扣减现金或缩放旧组合。

已复现：

```text
存量现金买入后：地区合计 110%，币种合计 110%
外部新增资金后：地区合计约 109.09%，币种合计约 109.09%
卖出后：地区与币种结果均为空
```

现有测试断言 `US 30% -> 40%`，但仍保留 `CN 70%`，实际上把错误的 110% 固定成了期望结果。

### 4.2 建议的数据契约

不要只传“若干权重然后局部相加”。建议优先传入各切片的本位币金额：

```json
{
  "portfolio_value_base": 100000,
  "region_values_base": {
    "cash": 50000,
    "cn": 20000,
    "us": 30000
  },
  "currency_values_base": {
    "CNY": 60000,
    "USD": 40000
  },
  "candidate_amount_base": 10000,
  "funding": "existing_cash",
  "funding_currency": "CNY",
  "instrument_region": "us",
  "instrument_currency": "USD"
}
```

使用金额完成交易前后变化，最后统一除以交易后总资产生成权重。这样更容易保持守恒，也便于验证每一步。

如果暂时保留权重契约，则必须严格采用以下公式。

### 4.3 存量现金买入

总资产不变：

```text
total_after = total_before
candidate_weight = amount / total_before
```

地区：

```text
after["cash"]             -= candidate_weight
after[instrument_region]  += candidate_weight
```

币种：

```text
after[funding_currency]    -= candidate_weight
after[instrument_currency] += candidate_weight
```

如果两个币种相同，两次变动自然抵消，币种暴露不变。

### 4.4 外部新增资金买入

先缩放所有旧权重，再加入候选资产：

```text
total_after = total_before + amount
old_scale = total_before / total_after
candidate_weight = amount / total_after

for every existing bucket:
    after[bucket] = before[bucket] * old_scale

after[instrument_region]  += candidate_weight
after[instrument_currency] += candidate_weight
```

### 4.5 卖出

必须明确卖出所得资金的结算币种。建议当前默认：

- 卖出所得先保留在标的计价币种；
- 不假设自动换成本位币；
- 未计入手续费与税费，因此使用“约”并保留警告。

地区：

```text
after[instrument_region] -= sold_weight
after["cash"]            += sold_weight
```

币种：

```text
卖出资产和所得现金属于同一币种，因此该币种总暴露保持不变。
```

如果以后支持“卖出后立即换成本位币”，必须增加独立选项和汇率/成本输入，不能静默转换。

### 4.6 必须增加的守恒校验

对所有成功计算结果执行：

```text
每个权重有限且 >= 0
abs(sum(region_weights) - 1) <= tolerance
abs(sum(currency_weights) - 1) <= tolerance
cash_weight_after 与 region["cash"] 一致
```

输入本身不守恒、缺切片或可能产生负权重时，返回未知并解释原因，不得修剪成零后继续输出。

### 4.7 UI 修改

`EvidenceCardView.RenderImpact` 当前只显示 `region_weight_after`，必须同时显示：

- 地区分布（交易前 → 交易后；
- 币种分布：交易前 → 交易后；
- 现金占比：交易前 → 交易后；
- 使用的资金来源币种；
- 权重无法计算时的具体缺失项。

不要只展示“交易后”而隐藏基线，否则用户无法判断变化大小。

### 4.8 必须增加的测试

1. CNY 现金买 USD/US 资产：现金和 CNY 各下降，USD 和 US 各上升，总和均为 1。
2. CNY 现金买 CNY/CN 资产：地区从 cash 移到 CN，CNY 总暴露不变。
3. 外部入金买 USD/US：旧权重先缩放，再加入候选资产，总和为 1。
4. 卖出 USD/US：US 降、cash 升，USD 总暴露保持不变。
5. 卖出金额超过持仓时只按可卖部分计算，并明确提示。
6. 输入权重初始合计不是 1 时 fail-closed。
7. UI 渲染测试同时断言地区和币种文本存在。

## 5. 工作包二：统一换汇费用的未知/零语义

### 5.1 当前问题

涉及文件：

- `python/caishenfolio_core/research/fx_paths.py`
- `src/Caishenfolio.Host/Notifications/FxAlertRuleEvaluator.cs`
- `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml`
- `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml.cs`

`PathCost` 文档规定：

```text
未填写 = 未知，绝不等于零
```

但当前只填写固定费、点差留空时，代码会把点差当成零，返回 `status=ok` 的净额。提醒设置也允许用户只填写固定费，却没有说明空点差会被当作零。

这会高估净到账并可能错误触发“净到账达到目标”提醒。

### 5.2 推荐契约

简化并明确为：

```text
variable_cost_pct = None  -> 比例成本未知，不能计算净额
variable_cost_pct = 0     -> 用户明确确认比例成本为零
variable_cost_pct > 0     -> 使用用户输入值

fixed_fee = None          -> 固定费未知或未提供
fixed_fee = 0             -> 用户明确确认固定费为零
fixed_fee > 0             -> 使用用户输入值
```

为了避免要求用户分别理解点差、比例手续费和滑点，UI 可以继续使用一个合计字段：

```text
比例成本合计%（点差 + 比例手续费 + 滑点）
```

但计算“净额”时，该字段必须显式填写。只填写固定费不足以证明比例成本为零。

### 5.3 提醒规则要求

`NetArrivalAbove` 必须同时满足：

- 比例成本字段已显式填写，包括显式 `0`；
- 固定费字段语义明确；
- 固定费币种可折算到目标币；
- 所需报价与持仓成本完整。

任一条件不满足：

```text
NetArrival = null
规则本轮未评估
说明缺少的字段
不得触发提醒
```

### 5.4 统一成本实现

建议提取一个公共成本计算器，供以下路径共同调用：

- 已持有币种直接换目标币；
- 本位币直接换目标币；
- 本位币经中间币换目标币；
- 分批兑换；
- 后台净到账提醒。

公共函数输入应明确：

- 毛到账金额；
- 执行腿数；
- 每腿比例成本；
- 固定费用究竟“每路径一次”还是“每腿一次”；
- 固定费币种及折算率。

不要继续让每种路径各写一套 `if frac is None` 分支。

### 5.5 必须增加的测试

1. 比例成本空、固定费 1：所有路径均为 `gross_only`，净额为 `None`。
2. 比例成本显式 0、固定费 1：净额等于毛额减固定费。
3. 比例成本与固定费都显式为 0：可计算净额且等于毛额。
4. 固定费币种不可折算：fail-closed。
5. 单段、两段、分批和后台提醒使用完全一致的费用语义。
6. UI 保存空白与显式 `0` 后，读取结果必须可区分。
7. 只填固定费的净到账提醒不得触发，并说明“比例成本未填写”。

## 6. 工作包三：取消“同日流水等于转账”的推断

### 6.1 当前问题

涉及文件：

- `src/Caishenfolio.Host/Portfolio/FxExchangeHistory.cs`
- `src/Caishenfolio.Host/Portfolio/LedgerTransaction.cs`
- `src/Caishenfolio.Host/Portfolio/PositionCalculator.cs`
- 账本录入与 CSV 导入/导出

当前成本计算先按日期汇总净变化，并把同日提现与入账的净额解释为账户转账。流水没有关联 ID，无法证明两笔业务相关。

已复现：

```text
第 1 天：100 CNY -> 2,000 JPY
第 2 天：提现 1,000 JPY，同时收到无关外部入账 1,000 JPY

当前结果：
2,000 JPY 全部沿用 100 CNY 旧成本

正确安全结果：
原 1,000 JPY 保留约 50 CNY 成本
新 1,000 JPY 进入未定价池
```

### 6.2 短期修复

在显式转账模型落地前：

1. 删除按日期净额合并逻辑。
2. 按 `TradeDate -> RecordedAt -> Id` 的稳定顺序逐笔重放。
3. 外币提现、消费、买入、手续费：按定价池/未知池比例释放。
4. 外部入账、利息、分红或来源不明的外币流入：进入未知池。
5. 两笔流水即使同日、金额相同，也不得自动抵消。

这一策略对真正的跨账户转账会偏保守：转出释放旧成本，转入成为未知。但它不会把外部资金伪造成有成本，符合 fail-closed。

### 6.3 正式修复：新增显式现金转账

建议增加领域级 `CashTransfer`，一次流水原子表达：

```text
from_account_id
to_account_id
currency
amount
fee
trade_date
```

语义：

- 本金只改变账户位置，不改变全局币种余额和成本池；
- 手续费从该币种余额和成本池中释放；
- 不需要依靠同日、同金额猜测；
- 转入/转出不能分开保存，避免只记一边。

可评估复用现有 `counter_account_id` 字段，但交易类型和验证必须独立清晰，不能冒充 `FxExchange`。

CSV 应新增明确的“转出账户/转入账户”列，并继续采用预览校验和内容哈希幂等。

### 6.4 旧数据处理

不要自动把历史同日提现/入账改成转账。可提供只读候选提示：

```text
发现疑似跨账户转账：同币种、同日、金额相同。
是否由用户确认关联？
```

只有用户明确确认后才能生成转账关联或冲正并重记。

### 6.5 必须增加的测试

1. 同日无关提现和入账不得相互抵消。
2. 同日先购汇再消费，剩余成本正确。
3. 同日先消费再外部入账，外部入账进入未知池。
4. 同日提现 1,500、外部入账 1,000：保留 500 旧资金成本 + 1,000 未知资金。
5. 显式跨账户转账保持全局成本不变。
6. 带手续费的显式转账只释放手续费对应成本。
7. 转账只有一边或账户不存在时整笔拒绝。
8. CSV 转账往返及重复导入幂等。

## 8. 工作包五：修正测试真实性和质量门禁

### 8.1 最大损失转换测试必须调用生产代码

当前 `MaxLossInputConversionTests` 在测试文件中复制了 `TryConvert`，即使真实 UI 转换以后被改坏，复制版本仍可能通过。

整改：

1. 从 `EvidenceCardView` 提取无 UI 依赖的生产类，例如：

```csharp
internal static class PercentInputParser
{
    internal static ParseResult ParseRequiredFraction(...);
}
```

2. View 和测试共同调用该实现。
3. 使用 `InternalsVisibleTo` 或现有桌面测试程序集访问内部方法。
4. 删除测试文件中的镜像算法。

### 8.2 修正“分批路径最优”假测试

当前测试先断言：

```text
split < held
```

随后允许：

```text
best_path in (held, split)
```

因此它没有验证分批路径最优。

在当前线性成本模型下，分批路径通常是两端路径的组合，不应凭空优于更好的单一路径。建议采取诚实方案：

- 把测试改名为“分批结果处于两条路径之间，且排序量纲正确”；
- 把质量门禁 #7 改为对应真实数学性质；
- 产品文案继续说明分批用于平滑时点不确定性，不保证最大到账。

只有未来实现阶梯点差、额度优惠、每笔上限等非线性成本后，才增加“分批真实最优”用例。

### 8.3 增加通用不变量测试

除样例数值外，增加性质/参数化测试：

- 组合权重之和始终为 1；
- 费用增加时净到账不得增加；
- 固定费为正时净额不得等于毛额；
- 未知费用不能产生 `status=ok` 的净额；
- 同币种现金转资产时币种暴露不变；
- 外部资金加入后所有旧权重按相同比例下降；
- 冲正后结果与原交易从未发生一致；
- 无关联流水不能仅因同日而合并。

## 9. 工作包六：清理 Python 依赖兼容警告

当前 Python 全量测试仍出现：

```text
RequestsDependencyWarning:
urllib3 (2.6.3) or chardet (7.4.3)/charset_normalizer (3.4.3)
doesn't match a supported version
```

整改步骤：

1. 在项目实际运行 venv 中记录 `requests/urllib3/chardet/charset-normalizer` 的版本及依赖来源。
2. 确认由 `akshare`、`yfinance` 或其他市场依赖带入的版本范围。
3. 在项目的运行时锁文件或约束文件中固定一组官方兼容版本。
4. 更新 Python 运行时依赖哈希。
5. 删除旧 venv，在干净环境重新供给依赖并跑全量测试。
6. CI 增加 `python -W error` 或针对依赖兼容警告的失败门禁，避免警告长期被忽略。

不要通过全局屏蔽 `RequestsDependencyWarning` 完成该项。
