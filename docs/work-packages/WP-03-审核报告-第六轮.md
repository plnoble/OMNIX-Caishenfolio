6. **C5-3：未关闭，存在顺序依赖与已存别名两条漏洞（P1）。**

7. **过度清理与身份丢失：一项新回归、一项仍未消除的顺序漏洞。**

   **C6-1 / P1，本次新回归：已有 Id 的半迁移规则不再补旧档位键。**

   输入旧设置：下限 `7.1000001`、`Id=D`、`Revision=0`、无 `LegacyRuleKeys`；旧状态只有 `FxBand|USD/CNY|汇率进入你设定的区间|rule:D@r0#band:7.1~-`，T 时已送达。这是身份已经回填、键格式兼容尚未完成的半迁移形状，也可能来自此前只写回身份的版本。

   新版 `NotificationSettingsStore.Load()` 调用 Reconcile 时，因为 Id 非空，`FxAlertRuleIdentity.cs:132` 判为非迁移，`:219` 完全不补别名。当前键变成 `D@r0#band:7.1000001~-`，旧键无法命中，T+30 分钟报价 7.2 会在升级当天重发；如果首轮 UNKNOWN，旧完整键也不会得到保活。`6ac0a48` 的旧分支会为同一输入补齐旧键，所以这是本次条件收紧带来的回归。

   “新创建的规则自带 Id”不意味着“所有自带 Id 的规则都是新创建”。应区分创建来源与持久化迁移状态，并能保留原显式身份自己的旧格式键；不能靠一条 `Id 为空` 同时证明这两件事。

   **C6-2 / P1，残留：新条目先拿走后续规则可匹配的身份，使后者随机换号并丢历史。**

   合成步骤：先 Save 无 Id 的 A（下限 7），再用编辑器将 A 改为 7.1 并保存，得到 A=D/r1，别名为空；记录其当前完整键 `D@r1#band:7.1~-` 在 T 已送达。随后提交 `[无 Id B(7.15,r0), 无 Id A(7.1,r0)]`，相当于在原无 Id 请求前插入一条新观察，A 的参数与已存版本完全匹配。

   `FxAlertRuleIdentity.cs:119` 只预留显式身份，未提前预留后续签名匹配所需的 D。B 无签名匹配，在 `:185` 先继承 D，`:264` 将 B 推到 r2。轮到 A 时，`:167` 因 D 已 taken 跳过其唯一正确的已存匹配，`:185` 给 A 随机 Q；A 只得到由请求 r0 构造的 `D@r0#band:7.1~-` 别名（`:221`），实际 D/r1 历史丢失。T+30 分钟报价 7.2，A 也被当作首次发送。

   如果顺序改为 `[A,B]`，A 可正确保留 D/r1。新版避免了两个输出共用 D，却没有保证 D 留给可确定匹配的原拥有者。这个顺序漏洞在旧实现也存在，不应全部归咎于新 `taken` 集合；但本次“继承＋幂等已收口”的结论仍不足。应先解决可确定的已存匹配，再对剩余条目分配身份。
