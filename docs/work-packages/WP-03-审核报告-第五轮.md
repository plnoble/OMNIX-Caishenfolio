1. **C4-1：原始反例已修，整体仍未关闭（P1，与 C4-2 同根）。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleIdentity.cs:102`、`:138`、`:144`、`:180`、`:189`、`:247`；`src/Caishenfolio.Host/Notifications/NotificationSettingsStore.cs:36`、`:61`。

   **成立条件：** 空设置库中首次保存两条无 Id 的 USD/CNY 区间规则，下限分别为 7、7.1。首次迁移得到派生身份 D 和独立身份 Q，版本均为 r0；Q 携带自己的旧完整键。随后 Load 按各自唯一 Id 比较自身，不再把另一档当成旧版本，当前键与版本保持稳定。原 C4-1 的这个具体输入已修复。

   **仍可触发的输入：** 先 `Save([A])`，A 是无 Id、下限 7 的规则，得到 D/r0，并已有其近期送达记录；再 `Save([原始无 Id A, 无 Id B])`，B 下限为 7.1；最后 Load。

   **会出什么错：** 第二次 Save 时，A 从签名匹配取得 D，但这个分支只更新 `reserved`，没有更新 `claimedDerived`；B 无签名匹配，`:189` 只检查 `claimedDerived`，不检查 `reserved`，又取得 D。Save 返回 A=D/r0、B=D/r1。随后 Load 的 `storedById[D]` 再次被 B 覆盖，A 被错误推进到 r2；A 原本的 D/r0 完整键没有被记录为它的新别名，冷却期内可以重发。

   **为什么是缺陷：** “Id 永远唯一”是后续加载、版本与 UI 定位的前提，但回退分配器仍能自行制造重复 Id，不需要调用方提交重复 Id。字典的键唯一不等于规则列表的 Id 唯一。应统一检查整批已预留／已认领身份，而不是维护两个会脱节的集合。

   **边界：** 对已由 `721ec42` 写成相同非空 Id 的两条规则，本版显式 Id 分支也原样放行，并不修复既存冲突；只有确认这类中间构建数据从未被使用，才能排除该升级输入，不能据此声称支持任意旧设置。

2. **C4-2：部分修复，仍能在半迁移批次中重复分配身份（P1）。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleIdentity.cs:114`、`:124`、`:173`、`:180`、`:189`。

   **成立条件：** 先迁移两条规则得到 D/Q，再提交 `[带 D 的第一条, 原始无 Id 第二条]`，无 Id 规则会跳过预留的 D，复用 Q；倒序亦成立。原来的最小两条输入已修。

   **触发输入：** W 为一条合法无 Id 区间规则。先 `Save([W,W])` 得到 D/Q；再提交 `[带 Q 的返回对象, W, W]`，即一个显式身份和两个无 Id 对象。

   **会出什么错：** Q 被预留；第一个 W 匹配 D；第二个 W 找不到未预留候选，回退分支却仍认为 D 尚未被认领，输出 **[Q,D,D]**。后两个规则完整键相同，独立冷却与按 Id 定位再次失效。这仍覆盖上一轮“显式 Q + 两条无 Id”反例，只是重复的身份从 Q 变成了 D。

   另外，显式 Id 只有在等于该规则**当前** DerivedId 时才进入 `claimedDerived`。已迁移规则改变币种对、保留原 Id 后，另一条无 Id 规则仍可能通过回退领取这个已在 `reserved` 中的 Id；“显式给出的 Id 全部不会被别人拿走”也不成立。

   **为什么是缺陷：** `reserved` 只约束签名匹配，没有约束最终发号；半迁移输入合法，分配器必须保证所有分支输出唯一。应补上述三条输入及显式 Id 与当前 DerivedId 不同的输入，断言每个身份只出现一次。
