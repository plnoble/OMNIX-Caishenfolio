WP-03 对抗性代码审查报告

审查范围：`git diff cb65b6d..3ee1da2`；交付提交完整 SHA 为 `3ee1da27549ceeb99acec76a3c6ee7d0eabb6479`。已阅读任务书的 A1–A11、D1–D11、风险，以及仓库协议。任务书写的原始基准不同，本次按用户指定的 `cb65b6d` 审查。

本轮只做静态代码审查；未运行构建、单测、冒烟、应用或复现程序，未访问真实账本。以下输入均为合成示例，结果由调用链和分支逻辑推导，不冒充运行证据。唯一写入是本报告；已有未跟踪交付报告未改动。结论：**必须修**。

1. **[P1] 补录更早的换汇、冲正资金来源，可以使原本合法的账本出现新负余额。**

   **文件:行：** `src/Caishenfolio.Host/Portfolio/PortfolioStore.cs:495–513`；`src/Caishenfolio.Host/Portfolio/PositionCalculator.cs:30–47`；CSV 同类过滤在 `src/Caishenfolio.Host/Portfolio/TransactionCsvImporter.cs:242–245,285`。

   **触发输入：** 银行账户先录入 2026-01-01 入金 100,000 CNY，再录入 2026-01-03 换出 100,000 CNY；随后补录 2026-01-02 换出 100,000 CNY。另一条路径是：入金并全额换汇之后，通过 `ReverseTransaction` 冲正那笔入金。

   **会出什么错：** 补录行在自己的交易时点看见 100,000，校验通过；重放到 01-03 时只因该行不在 `watched` 中便不检查，最终 CNY 为 -100,000。冲正入金时，本批没有 `FxExchange`，校验直接返回；重放取消入金后同样得到 -100,000。冲正一笔已被后续换汇消耗的换入交易也有同类问题：冲正行与原行被重放过滤，后续换汇未重新检查。

   **为什么是缺陷：** 这些负余额由升级后的新写入造成，不是 D2 要保留的既有缺口。D1 的写入约束不能仅验证新增行执行之前的瞬时余额，而忽略此次写入对后续资金链的影响。修复应识别本次新增或加重的缺口，同时保留原有历史负余额，不能改成全量否决老账。

2. **[P1] 无资金的普通账户转账可以为换汇“提供余额”，扩大了 D3 的豁免面。**

   **文件:行：** `src/Caishenfolio.Host/Portfolio/PortfolioStore.cs:495–501,516–520`；`src/Caishenfolio.Host/Portfolio/PositionCalculator.cs:130–134`；`src/Caishenfolio.Host/Portfolio/TransactionCsvImporter.cs:241–245`。

   **触发输入：** 两个余额均为 0 的 Bank 账户 A、B；先记 A→B 转账 100,000 CNY，再记 B 换出 100,000 CNY、换入 2,000,000 JPY。使用正常的 `LedgerTransaction.Transfer` / `FxExchange` 和 `AddTransactions`，或导入相同 CSV，即可构成此输入。

   **会出什么错：** 转账未受余额校验，A 变成 -100,000，B 获得 100,000；换汇看到 B 有足额资金便通过。整组操作没有任何期初或入金，却产生 JPY 和普通银行账户透支。CSV 预览也会把转账作为可用资金来源。

   **为什么是缺陷：** 这里没有 `OpeningCash` / `OpeningPosition`，也没有证券融资买入。普通转账事实上成了新的透支豁免，绕过了“换汇不豁免”的 D3 和 D1 写入约束。此路径不需要手改 SQLite，也不依赖界面漏洞。

3. **[P1] 旧提醒状态遇到升级后首次 UNKNOWN，会伪造退出并在冷却期内重发。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/AlertGatekeeper.cs:181–185,210–220`；新 UNKNOWN 键生成在 `src/Caishenfolio.Host/Notifications/FxAlertRuleEvaluator.cs:201–207`。

   **触发输入：** 旧 `alert-state.json` 中存在旧键 `Kind|Symbol|Title`，`WasInRange=true`，09:00 已送达，冷却 12 小时。升级后 09:10 首次扩展检查缺报价或整体失败，`notEvaluated` 只包含带规则身份的新键；09:20 报价恢复，条件始终满足。

   **会出什么错：** 09:10 没有触发 alert，所以不会执行 `AdoptLegacy`。旧键既不在新键组成的 UNKNOWN 集合中，也不在 `firing` 中，于是被写成 `WasInRange=false`。09:20 新键采用这个旧记录，因 `!previous.WasInRange` 立即发送，绕过尚未结束的冷却。若首次检查整体失败，多条旧提醒都会走这条路径。

   **为什么是缺陷：** 没有发生真实退出/重入，只是升级后的键格式与旧状态不一致。违反 A8/A9、D6，并回退 WP-02 的 UNKNOWN 语义。当前 A9 测试（`tests/Caishenfolio.Host.Tests/AlertIdentityTests.cs:118–147`）只覆盖“升级首轮立即满足”，未覆盖这条两轮迁移链路。

4. **[P1] 规则 id / revision 没有接入创建和保存流程，实际规则仍会共享身份并漏发。**

   **文件:行：** `src/Caishenfolio.Host/Notifications/FxAlertRuleEvaluator.cs:32–38,85–102`；真实创建入口 `src/Caishenfolio.Desktop/Wealth/PortfolioSettingsWindow.xaml.cs:448–457`；组键 `src/Caishenfolio.Host/Notifications/AlertGatekeeper.cs:136–139`。

   **触发输入：** 在设置页创建两条 CNY/JPY/USD 的净到账规则，阈值都为 1,000 USD，点差都为 0，固定费分别为 0 和 2 USD。第一轮毛到账 1,001 USD，只有第一条满足并送达；冷却期内毛到账升至 1,003 USD，第二条首次满足。

   **会出什么错：** 两条规则都保持 `Id=""`、`Revision=0`；`StableId` 仅由类型和币种生成，`Level` 都是 `amt:1000`，费用不同不影响键。第二条首次满足时继承第一条的冷却而被压掉。生产代码也没有为规则分配持久 id 或推进 revision 的流程，只有把默认值传给 alert 的代码。

   **为什么是缺陷：** D5 要求的是规则身份，不是类型和币种的分类身份。新增两个字段并不能代替实际身份管理。另有同根碰撞：档位按 `0.######` 舍入，而阈值解析/比较没有六位精度限制；下限 `7.1000001` 与 `7.1000002` 会成为同一个 `band:7.1~…`，连“不同阈值独立提醒”也不能普遍成立。消息/备注没有入键这一点是正确的，但不能消除上述漏发。

5. **[P2] “现在换”结论仍以毛额显示到手金额和基准优势，净额改造没有完成。**

   **文件:行：** `src/Caishenfolio.Desktop/Wealth/FxCarryView.xaml.cs:559–584`；`python/caishenfolio_core/research/fx_paths.py:864–886`；卡片标题 `src/Caishenfolio.Desktop/Wealth/FxCarryView.xaml:290`。

   **触发输入：** 持有 2,450 JPY，历史成本 100 CNY；USD/JPY=150，USD/CNY=7.2；持有路径点差 0、固定费 3 USD，新资金路径成本为 0。另一个输入是把持有路径固定费留空。

   **会出什么错：** 有费用时，毛到账约 16.33 USD、净到账约 13.33 USD，净盈亏为 -4 CNY，相对零费用基准的净优势为 -4%；但“现在换能到手”卡仍先显示未标毛额的 `16.33 USD` 和 `比基准 +17.6%`，再显示净亏损。费用留空时，卡片虽增加“净额未知”，仍给出同一个未标毛额的正向基准结论。

   **为什么是缺陷：** `advantage_now` 仍取 `advantage_gross`，UI 也仍读取它，没有使用已有的净优势。D7/A10 要求结论使用净额、不可知时不拿毛额作答案；只替换盈亏字段不足以满足要求。新增 `PnlVsCostNetInBase` 本身没有回落毛额或补 0，但整张结论卡仍混用口径。

6. **[P2] 历史最低余额被写成当前余额，恢复资金后仍显示“自那天起就是负的”。**

   **文件:行：** `src/Caishenfolio.Host/Portfolio/PositionCalculator.cs:433–445`；`src/Caishenfolio.Host/Portfolio/PortfolioWorkspace.cs:108–115`；`scripts/ui_smoke.ps1:1316–1320`。

   **触发输入：** 旧账在 01-05 换汇后曾为 -100,000 CNY，01-06 入金 150,000 CNY，此后打开总览。也可以在升级后新增一笔合法融资买入，使现金首次为负。

   **会出什么错：** `HistoricalShortfalls` 保留历史最低值，余额恢复时直接返回，不更新或结束这段缺口。当前现金已为 +50,000，文案仍断言“现金是 -100,000”“自 01-05 起就是负的”。新产生的融资负余额也被解释为“那时还没有余额约束，不是当前操作造成的”，但代码没有升级边界或原因判断。

   **为什么是缺陷：** D2 要求如实标注历史，不能把“曾经最低”描述成“现在仍然”。新增冒烟断言还固定要求这个错误的当前余额措辞：此前 `Invoke-LedgerTypeSwitchCheck` 已记录入金 500 和买入 10（脚本 1107–1142 行），却仍要求“现金是 -100”。应区分当前余额、历史最低值和负余额原因，并同步修正断言。

7. **[P2] 拒绝信息把合法 decimal 精度的非零缺口舍入成 0。**

   **文件:行：** `src/Caishenfolio.Host/Portfolio/PortfolioStore.cs:525–526`；`src/Caishenfolio.Host/Portfolio/TransactionCsvImporter.cs:300–301`。

   **触发输入：** 余额 100,000 CNY，换出 100,000 CNY，手续费 0.001 CNY。领域工厂允许非负 decimal 手续费，并未限制为两位小数。

   **会出什么错：** 校验用精确的 100,000.001 正确拒绝，但消息统一使用 `#,0.##`，显示“账上有 100,000，这笔要 100,000，差 0”；CSV 行错误同样如此。

   **为什么是缺陷：** D4 要求解释真实差额。系统既接受该精度参与余额判断，就不能在解释拒绝原因时把缺口变成零。应保留足以表达差额的精度，或在明确的输入规则中拒绝不支持的精度。

8. **[P2] A1/A3 的金额断言不能识别错误余额或错误差额，不能作为 D4 完整验收证据。**

   **文件:行：** `tests/Caishenfolio.Host.Tests/BalanceConstraintTests.cs:42–45,74–75`。

   **触发输入：** 保持拒绝且不写账，只把 A1 错误消息误实现为“账上有 100,000，这笔要 100,000，差 0”；A3 错误消息为“账上有 100,000，这笔要 100,001，差 0”。

   **会出什么错：** 两个错误消息都会通过目前的金额相关断言。A1 的 `Contains("0")` 已被 `Contains("100,000")` 蕴含，不能验证可用余额为零；A3 的 `Contains("1")` 无法区分所需金额中的数字与差额为 1。

   **为什么是缺陷：** 测试名称和注释声称钉住“有/要/差”，实际只钉住若干子串。这里没有发现故意删除或放宽既有测试，但新增验收证据不能支持它声称覆盖的数值语义；应分别断言三个带标签的完整数值，并覆盖手续费及交易时点。

其余审查结果：

- **D1 / D4 的正确部分：** 校验位于 `AddTransactions` 的 SQLite 事务内（`PortfolioStore.cs:258–260`），正常表单、`Workspace.Record`、直接调用 Store 和 CSV 提交都会进入；直接超额换汇会在 INSERT 前抛错。检查使用重放到该行之前的余额，需求额为 `CashAmount + Fee`，没有漏掉源码定义的来源币种手续费。问题是第 1、2 条的资金链缺口，而不是只有界面提示。
- **D2 / A5：** `LoadState` 仍调用不带拒绝回调的 `Replay`（`PortfolioStore.cs:1131–1132`），单纯既有负现金不会因新增规则打不开。diff 未新增历史流水迁移、UPDATE 或 DELETE，也未修改 schema。仓库原有显式删账户/打新同步删行属于基准已有行为，并非本次升级因负余额触发的清账；未把它们算成本提交新缺陷。第 6 条是标注失真。
- **D3：** `OpeningCash` 仍提供期初现金，`OpeningPosition` 不新增现金支出；股票买卖分支未改，未发现针对证券账户的换汇豁免。普通账户转账形成的额外透支通道见第 2 条。
- **A6：** 普通“入金不足 + 超额换汇”CSV 会标记该行错误，并在显式选择跳过错误行后提交其余行；预览与提交都没有解决第 1、2 条的绕过。
