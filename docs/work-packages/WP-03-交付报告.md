### 0.3 顺带收口精度碰撞（Codex `#4` 同条提到）

`FxAlertRule.Level` 原来按 `0.######` 舍入，而阈值解析没有同等限制：`7.1000001` 与 `7.1000002`
都落进 `band:7.1~-`，两条用户分开建的规则共享一个冷却。改成 `G29`（decimal 的往返格式：不用科学
计数法、不丢有效位、仍去掉尾零），既分得开，也**不让用户已有值的键漂移**：
`1000 → amt:1000`、`0.00 → amt:0`、`3.0 → pct:3`、`7.10~8 → band:7.1~8`（有测试钉住）。

| 5 升级当天不得在冷却期内重发（D6） | 迁移把冷却记录搬到新键；**迁移失败即推迟**：`Load` 不落盘并把**未结算**的规则返回给调用方，`Save` 抛 `AlertStateMigrationException`（设置页原样报错）。为配合这条，**没有身份的规则继续用六位档位渲染 key**（旧构建用的那把键） |
| 6 不碰 WP-04 的 #1/#2/#5 | 一行未碰（§10.2） |

**机制**（旧键怎么推出来、新键怎么对上）：

- 旧键 = `{Kind}|{Symbol}|{Title}|rule:{到达时的 StableId}@r{到达时的 Revision}#{到达时的 LegacyLevel}`。
  全部由**到达时**（结算前）的规则形状推出，所以「两条同派生身份、档位不同」的旧规则各自能找到**自己**那把键，
  包括被消歧成随机身份的那条（旧构建把它记在派生身份下）。
- 新键 = 结算后规则的 `KeyOf(Probe(rule))`。
- 候选若正好是**同批另一条规则的当前键**则跳过（那把键属于那条规则的历史）。
- 幂等与重试：迁移不需要任何持久化记忆，失败后下一次 Load 重新推导同一组映射。

**统筹点名的五条残余，逐条为什么消失**：

### 5.6 的当时理由（保留，不改写成现在的结论）

**当时停手的理由（如实说明，不是「修不动」）**：这些条目全部落在同一处设计张力上——
「永久别名」这个做法本身**没有生命周期与归属的明确语义**，只能靠一条条补丁逼近。逐条打补丁已经出现
「修一条、冒出两条」的形态（第五轮修了 C5-1～C5-3，第六轮又开出 C6-1/C6-2）。正确的收口不是继续打补丁，
而是**换机制**：迁移时**一次性把旧键对应的状态记录改写成新键**（`alert-state.json` 的所有权本来就在我们手里），
落地后不保留永久别名——这样上面这一整类边界都会**由构造消失**。

这属于设计取舍（要动状态文件的写入路径），我不在没有征得同意的情况下自行改掉已经过两轮验收的接法。
统筹退回时点名的三条（`#1` 两个不同档位、`#2` 超六位小数、`#3 幂等`）在 `1f03a04` 上都有
「先红后绿」的证据并且仍然全绿；§10 把这五条残余按复现输入列清，供统筹决定是否立项。

## 8. 关键口径（落地说明）

- **约束只判本批的换汇行**：`ValidateBalances` 重放「已有 + 本批」，但只对**本批里的 `FxExchange`**
  报错。所以：老账本里已有的负余额永远不报错（D2）；同一批里先入金后换汇是允许的（顺序按
  `TradeDate → RecordedAt → Id`，与重放一致）；冲正、转账、卖出都不受影响。
- **余额的时点**：判定用的是那一行**发生当时**的余额（重放到该行之前），不是今天的余额。
- **手续费**：换汇行的手续费计入换出方的支出（和重放一致），所以「要多少」= 换出金额 + 手续费。
- **数字展示**：拒绝文案用 `#,0.##`，不显示科学计数法，也不把未知当 0。
- **身份与档位的稳定性**：`StableId` 在没配 `Id` 时由 `Kind:Pair:Base/Target/Held` 派生；
  `Level` 只由档位值构成。改标题、改备注、改冷却都不会改键。
